# ADR-003: 部署与信任模型（多用户共享 Server）

- **Status:** ACCEPTED
- **日期:** 2026-09-29
- **关联:** `PRODUCT.md` §4/§7、`REQUIREMENTS.md` NFR-6 / A-2 / Q-1 / Q-2 / Q-5 / FR-24、`ADR-001`、`PROTOCOL_SPEC.md` §1/§3、`CLIENT_SPEC.md`、`SERVER_SPEC.md`
- **来源:** 基础产品启动前的部署/信任模型决策（缺口收敛评审之后的下一阶段）

---

## Context

在写实现计划之前，必须先回答一个此前被显式延后的问题：**Server 和 Client 各自跑在哪、谁连谁、信任边界在哪。**

这个问题同时决定三件事的形态：

1. **安全基线的厚度**——`REQUIREMENTS.md` NFR-6 原话是"认证、授权、沙箱等安全要求不在本文件定义，由后续安全规格承担（待建）"，即安全被延后；
2. **技术栈的形态**——Client 是否只是网页、Server 是否需要长连接与持久化、是否要处理多用户；
3. **`A-2` 假设是否成立**——`REQUIREMENTS.md` A-2 假设"一套硬件在同一时刻只由一位工程师操作"。

同时，`Q-1`（谁有权确认有副作用的动作）、`Q-2`（Record 谁能查看）、`Q-5`（身份体系）一直挂着未决，它们必须在接口硬化之前定下来，否则后加是破坏性变更。

本次决策的结论是：**采用"多用户共享一个 Server、每位工程师独占自己的测试台"的部署形态**，并把安全从"可延后"提升为"最小基线，MVP 前置"。

---

## Decision

### 1. 部署形态

* 一个 **Server** 部署在**实验室内网**，可被多位工程师的 **Client** 连接。
* 每位工程师运行一个 Client；**每位工程师独占自己的测试台（硬件）**，硬件不在工程师之间共享。
* Client 与 Server 之间维持一条**持久双向连接**（沿用 `PROTOCOL_SPEC.md` §1），一 Client 一 `session`，一 `session` 内可并存多个 Workflow（沿用 `PROTOCOL_SPEC.md` §3）。

### 2. 信任边界

* **实验室内网受信**，但 Server 只接受**已认证**的 Client。
* Server 不暴露到公网；跨网/云部署不在本决定范围内。

### 3. 身份与认证

* Server **自建本地账号**（用户名 + 密码/令牌），自行管理用户与会话；不做组织 SSO/OIDC 联邦（留作后续可选项）。
* `session.hello` 携带认证凭据；认证失败返回 `protocol.error`（新增 code `auth_failed`，致命：断开）。
* `user_id` 从"预留字段"升级为**握手后必填、且由 Server 校验**。
* 需要最小账号管理面（创建 / 禁用 / 改密）；完整目录服务、角色体系不在本决定范围内。

### 4. 传输安全（v0.1 不强制 TLS）

* **v0.1 不要求 TLS**：MVP 在受信实验室内网运行，明文传输可接受。
* 这是一个**传输层**关注点：后续启用 TLS **不需要改动应用层协议**（握手、消息格式、信封、能力调用都不变），因此推迟的成本很低。
* 启用时机与终止点（Server 直挂 / 反向代理）留给实现或后续安全规格决定。
* **风险登记**：在启用 TLS 之前，凭据与 Evidence 在内网可被嗅探。此决定以"内网受信 + 明确接受该风险"为前提；若部署环境不满足，应在实现阶段提前启用 TLS。

### 5. 授权：副作用确认（关闭 Q-1）

* **只有提交该 Workflow 的工程师本人**可以确认该 Workflow 中有副作用的动作。
* 其他已认证工程师**不能**替他人确认，即使能看到该 Workflow（本版本也看不到，见 §6）。
* 依据：`PRODUCT.md` 产品原则 1"工程师始终掌控"；因每人独占自己的测试台，不需要更高级别审批。

### 6. 可见性：Record（关闭 Q-2）

* Record **默认仅提交人可见**（列表与详情都按当前认证用户过滤）。
* Report 由工程师自行对外分享；本系统不做团队可见/角色化可见。
* **导出到第三方 Knowledge Base 由提交人自行决定**：提交人可显式发起导出；KB 是否接收由其审核人员决定，本系统不追踪审核状态（详见 MVP 范围说明）。

### 7. 隔离与并发

* 一个 Client 对应一个 `session`；`session` 归属于某个 `user_id`。
* 同一 `session` 内多 Workflow 并发（NFR-4）不变。
* **副作用 Step 串行仍按 `session` 维度**（`WORKFLOW_SPEC.md` §4.4）：因为每位工程师独占自己的测试台，跨 session 的副作用冲突不存在。
* **不引入硬件资源/目标（resource/target）模型**——这是本决定最重要的"不做"。

### 8. A-2 的澄清

* `A-2`（"一套硬件在同一时刻只由一位工程师操作"）**继续成立**，但措辞需要澄清为：**每位工程师独占自己的测试台**，因此不存在多人争用同一硬件。
* 后续如需支持"共享测试台"，必须重开资源模型（本决定明确不覆盖）。

### 9. NFR-6 的重新定位

* NFR-6 原文"安全要求由后续安全规格承担（待建）"**需要修订**：本 ADR 即为**最小安全基线**，在 MVP 前生效。
* 仍然**延后**的部分：沙箱、多租户、审计/防篡改、完整角色体系。

### 10. Q-1 / Q-2 / Q-5 状态

| 开放问题 | 结论 |
|---|---|
| **Q-1** | **关闭**：仅提交人本人可确认副作用动作（§5） |
| **Q-2** | **关闭**：Record 仅提交人可见（§6） |
| **Q-5** | **部分落地**：引入 `user_id` 且必填、校验；但不做完整身份目录与角色体系（§3） |

---

## Rejected Alternatives

* **严格单机（Server 与 Client 同机、只走 localhost）**：最简单、零安全负担，但不满足"多位工程师共享 Server"的目标，且一旦要"笔记本 + 实验室服务器"就要重新论证。被否。
* **跨网 / 云 Server**：需要完整安全规格（认证、传输加密、数据出网合规），MVP 风险过高。被否。
* **组织 SSO / OIDC 作为 MVP 方案**：最规范，但依赖外部 IdP 与联调，MVP 集成成本高、外部依赖不可控。作为**后续演进方向**保留，不作为 MVP 方案。
* **轻身份（只认名字/工号，不设密码）**：在共享 Server 上任何内网客户端都能冒充他人，Record 隔离与 Q-1 授权形同虚设。被否。
* **mTLS 客户端证书**：安全强度高，但证书签发/轮换/吊销的运维成本对 MVP 过重。被否。
* **角色化审批（高风险动作需主管批准）**：需要角色模型与审批流；因每人独占自己的测试台，收益不足以支撑成本。被否。
* **团队全员可见 Record**：便于复盘，但日志/证据可能含敏感信息，且与"Record 仅提交人可见"的最小授权面冲突；显式分享由工程师用 Report 完成。被否。
* **共享测试台（需资源模型）**：会重开我们此前明确关闭的硬件资源模型，范围大幅扩大。被否——选择"每人独占自己的测试台"。

---

## Consequences

**正面：**

* 安全从"待建"变为"最小基线 + MVP 前置"，避免了后加认证导致的破坏性协议变更。
* `A-2` 保持成立，**不需要引入资源模型**，`D-B6` 的会话级副作用串行继续够用。
* `Q-1`、`Q-2` 关闭，接口（确认、Record 查询）可以按最小授权面直接实现。

**需要落实的改动：**

* `PROTOCOL_SPEC.md`：`session.hello` 携带凭据；新增 `auth_failed` 错误码（致命）；`user_id` 握手后必填并由 Server 校验；`record.list` / `record.get` 必须按 `user_id` 过滤；新增导出消息（见 MVP 范围说明）。
* `REQUIREMENTS.md`：修订 NFR-6 措辞（安全基线已由本 ADR 承担）；关闭 Q-1/Q-2；更新 A-2 措辞；更新 FR-24（MVP 提供导出半边）；补 MVP 范围。
* `CLIENT_SPEC.md` / `SERVER_SPEC.md`：登录与会话、账号管理最小面、导出入口、授权校验。
* `ARCHITECTURE.md`：补部署视图（多 Client → 一个 Server，实验室内网）。
* `RECORD_SPEC.md` / `REPORT_SPEC.md`：导出对象（Record 默认 / Report 可选）与格式说明。

**仍然延后：**

* 沙箱、多租户、审计/防篡改、完整角色体系、组织 SSO 联邦、共享测试台资源模型、跨网/云部署、传输加密（TLS）。
