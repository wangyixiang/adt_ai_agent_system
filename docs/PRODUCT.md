## 1. 产品描述（本文件的唯一输入）

> 这个产品是一个 HiL 诊断辅助系统。测试中，工程师用自然语言报告问题，系统辅助工程师搜集信息、诊断问题、解决问题，最后系统保存完整记录，可以根据用户是否需要，生成完整的报告。

本文件以下所有内容都必须能追溯到这段描述或下文 §8 记录的产品决策；无法追溯的内容不应出现在这里。

---

## 2. 一句话定位

面向 HiL（Hardware-in-the-Loop，硬件在环）测试的诊断辅助系统：工程师用自然语言报告问题，系统协助收集信息、定位原因、建议或（经工程师确认后）执行修复，结束时保存完整记录，并在用户需要时生成报告。

---

## 3. 问题陈述

HiL 测试中出现异常时，工程师排查通常面临这些反复出现的痛点：

* 信息分散在多个日志、工具和设备状态里，需要人工逐一收集、拼凑。
* 诊断依赖个人经验，同类问题在不同工程师、不同时间会被重新排查一遍。
* 排查过程和结论常常没有被完整记录，事后凭回忆补记，既费时又容易遗漏关键依据。

> 说明：第三条痛点里"同类问题被重复排查"，本产品选择的应对方式是**先把每次诊断完整、忠实地记录下来**（Record），本系统内部不构建检索或知识复用能力——但这不等于"检索这件事完全不做"：系统可以对接第三方 Knowledge Base 做检索，检索逻辑在第三方系统内；本系统产生的 Record 未来也可能被沉淀进该第三方系统，只是这不在当前版本范围内。两者是不同层次的问题，见 §7.2、§8 D-5。

---

## 4. 用户与角色

| 角色 | 与系统的关系 |
|---|---|
| **工程师（User）** | 唯一的直接用户：报告问题、补充信息、确认修复动作、确认问题是否解决、决定是否生成报告 |
| **集成开发者** | 间接用户：通过 Capability 机制把具体测试设备/工具接入系统 |
| **报告读者** | 报告的接收者（例如同事、主管）。他们不一定使用系统，系统不为他们提供独立的功能 |

"用户是否需要报告"中的"用户"即上表中的工程师。

## 5. 核心场景

```text
工程师发现异常
   ↓（自然语言描述）
系统开始一次诊断（Workflow）
   ↓
系统逐步收集证据（读日志、查设备状态……），工程师可随时查看进展、补充信息
   ↓
系统提出原因假设，并展示支撑该假设的证据
   ↓
解决问题，分两种方式：
   ├─ 建议：系统给出修复建议，工程师自行执行，并反馈结果
   └─ 受控执行：系统提议一个修复动作，工程师确认后才执行
   ↓
系统收集证据验证问题是否消除
   ↓
工程师确认问题已解决（或选择放弃/取消）
   ↓
系统保存完整记录（Record）
   ↓
工程师需要时，基于记录生成报告（Report）；不需要则不生成
```

---

## 6. 产品原则

1. **工程师始终掌控。** 任何会改变硬件或系统状态的动作，必须先经工程师明确确认；"问题是否解决"由工程师判定，不由系统判定。
2. **结论必须可解释。** 系统给出的原因判断，必须同时展示它依据的证据，以及哪些部分尚未被验证。
3. **记录忠实于事实。** 记录只包含实际发生的步骤、实际获得的证据和实际发生的人工决定；报告只基于记录生成，不引入记录之外的事实。
4. **领域中立。** 核心系统不绑定任何具体 HiL 平台或协议，领域相关的能力一律通过 Capability 接入。

## 7. 范围

### 7.1 范围内

* 自然语言问题提交
* 证据驱动的逐步诊断（每步基于最新证据决定下一步）
* 诊断进展与证据的可见性
* 两种解决方式：建议、经确认的受控执行
* 修复后的验证
* 完整记录的保存
* 按需生成报告
* 通过 Capability 接入不同的测试设备/工具
* 对接第三方 Knowledge Base 进行检索，作为诊断的辅助输入（v0.6 补充明确；检索逻辑在第三方系统内，见 §7.2、§8 D-5）

### 7.2 非目标

* **不是测试台的控制软件**：系统通过 Capability 与既有设备和工具集成，不取代它们。
* **不追求完全自主修复**：有副作用的动作一律需要工程师确认。
* **不提供审计或防篡改保证**：记录用于内部参考和生成报告，不作为审计证据链，不承诺不可篡改，也不面向合规认证。
* **不自动生成报告**：报告只在用户明确要求时生成。
* **不产出面向认证机构的正式文件**。
* **不绑定具体 HiL 平台、硬件协议或行业**。
* **不在本系统内建设知识库或历史案例检索能力**（v0.5 新增，v0.6 澄清）：本系统不实现自己的检索引擎或案例匹配逻辑（这部分交给第三方 Knowledge Base 承担，系统可以对接、查询它——见 §7.1）。系统保证每次诊断的完整记录被忠实保存（见 §5、§8 D-5），也保证工程师可以查看自己的历史 Record（§7.1），这是"记录可查"和"对接外部检索"，不是"自建知识检索"。本系统产生的 Record 未来可能被沉淀/导出到该第三方系统，这是已确认的方向，且**出站已落地为 FR-24 的"导出半边"**（提交人按需发起，P4d；KB 侧的接收与检索不在本系统内——见 §8 D-5、`REQUIREMENTS.md` FR-24、`ADR-005`）。
* **不做测试用例自动生成、不做测试执行编排**（v0.5 新增）：系统的介入点从"问题已经发生"开始，不涉及测试计划制定或测试自动化执行本身。
* **不对被测对象（DUT）的软件/固件进行代码级修复或生成修复建议**（v0.5 新增）：D-2 中的"受控执行"作用于测试环境与工具（通过 Capability），不涉及对被测系统代码本身的修改建议。

## 8. 关键产品决策

| 决策 | 内容 | 影响 |
|---|---|---|
| D-1 | 领域中立，不绑定汽车/航空/工业等具体领域 | 核心 Spec 不得出现具体设备协议；领域能力放在 Capability 层 |
| D-2 | 解决问题支持两种方式并存：建议、经确认的受控执行，具体用哪种视问题而定 | Capability 需要能声明"是否有副作用"；有副作用的动作需要确认机制 |
| D-3 | 不要求记录可审计、不可篡改 | 存储层不做防篡改设计；记录只要求完整、可读 |
| D-4 | 报告完全按需生成，由用户触发 | 报告不是诊断流程的一部分，需要独立的触发入口 |
| D-5（v0.5 新增，v0.6 澄清） | **系统不在内部构建知识库/检索引擎/案例匹配逻辑**——即使"同类问题被重复排查"仍是真实痛点，也不通过在本系统内建设检索能力解决。**但这不排斥对接第三方（外部）Knowledge Base 做检索**：检索逻辑在第三方系统内，本系统只是消费者。本系统产生的 Record 是否会被沉淀/导出到该第三方系统，供后续检索复用，是已确认的产品方向，**其"导出半边"（出站）已于 P4d 实现（FR-24、`ADR-005`）**，不改变本决定 | REQUIREMENTS.md 中原 FR-15（相似问题检索）标记为已删除，不再作为规划项；Record 的价值止于"忠实保存、可查看"（§7.1），不承担"系统内可检索复用"的目标；`RECORD_SPEC.md`（已建成，v0.11）设计上不与"未来可能被导出到第三方系统"这个方向冲突；**导出通道的出站已实现**（P4d），KB 侧的检索（FR-23）仍未实现 |

> 说明：D-5 与 v0.3 §8 的处理方式不同。v0.3 把相似问题检索列为 P1（"以后会做，先不做"），v0.5 把它改为明确的非目标（"这次决定不在这个系统里做"）。v0.6 进一步澄清：这个"不做"指的是"不自己造检索引擎"，不是"不能查任何知识库"——对接第三方系统做检索，以及未来把 Record 导出给第三方系统，都不违反这条决定。如果未来要在本系统内部自建检索/知识库能力，才需要重新打开这个决策。

## 9. 成功标准

以下是需要被度量的方向，**具体目标值待取得现状基线后再定**，本文件不预设数字。

| 方向 | 度量思路 |
|---|---|
| 诊断更快 | 从问题提交到工程师确认解决的耗时，对比无系统时的基线 |
| 记录不再靠回忆 | 已结束的诊断中，有完整记录的比例 |
| 建议被采纳 | 系统给出的修复建议/提议动作，被工程师采纳的比例 |
| 报告有用 | 工程师主动生成报告的次数；生成后是否需要大量手工修改 |

## 10. 术语

| 术语 | 含义 |
|---|---|
| User Request | 工程师提交的自然语言问题描述 |
| Workflow | 针对一个 User Request 的一次完整诊断-解决过程 |
| Step | 诊断过程中的一次具体动作（读日志、只读检查、经确认的修复动作等） |
| Evidence | Step 产生的观察结果，是诊断和验证的依据 |
| **Record** | Workflow 结束后保存的完整记录：原始问题、全部 Step、全部 Evidence、全部人工决定（确认/拒绝/反馈）、最终结果。只要求完整、可读，不承担系统内检索/知识复用的目标（§8 D-5），但设计上不应排斥未来被导出到第三方 Knowledge Base |
| **Report** | 用户需要时，基于一份 Record 生成的人类可读文档。可多次生成，生成不改变 Record |
| **（第三方）Knowledge Base** | 本系统之外、由其他系统承载的知识库。本系统可以对接它做检索（作为诊断的辅助输入），未来也可能把 Record 沉淀进去；本系统不承担该知识库本身的构建、检索算法或维护职责（v0.6 新增） |

`Record` 与 `Report` 是 v0.3 引入的概念，v0.5/v0.6 未改变其定义，只补充了与第三方 Knowledge Base 的关系。这两个概念后续已由专门文档覆盖：触发时机见 `WORKFLOW_SPEC.md` §12，结构见 `RECORD_SPEC.md` §3，内容约束见 `REPORT_SPEC.md`，协议消息见 `PROTOCOL_SPEC.md` §10、§11。
