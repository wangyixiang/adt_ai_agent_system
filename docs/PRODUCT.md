# PRODUCT.md

- **Version:** v0.2
- **层级:** Product — 为什么做
- **修订说明 (v0.2):**  报告改为完全按需生成，客户/工程师主动要求才生成，不是每次诊断的必需产出。

---

## 1. 一句话定位

一个面向 HiL（Hardware-in-the-Loop）测试场景的人机协同诊断辅助系统：工程师用自然语言报告问题，系统协助收集信息、定位根因、在授权范围内建议或执行修复，并为每一次诊断留下的完整记录，按需生成报告。

---

## 2. 问题陈述

HiL 测试中出现异常时，工程师排查通常面临几个反复出现的痛点：

* 信息分散在多个日志、工具、设备状态里，需要人工逐一收集拼凑。
* 诊断思路依赖个人经验，同类问题在不同工程师、不同时间会被重新排查一遍，经验不容易复用。
* 诊断过程和最终结论往往没有被结构化地记录下来——记录如果是事后靠回忆补的，既费时又容易失真、遗漏关键依据，也不利于后续复盘和知识沉淀。

本产品**不绑定具体 HiL 测试领域**（汽车、航空航天、工业自动化等均可能是使用场景），核心能力通过可插拔的 Capability 机制对接不同的测试设备/系统，而不是为单一硬件平台定制。

---

## 3. 目标用户

* **一线 HiL 测试工程师**（主要用户）：报告问题、参与诊断、确认修复动作、确认问题解决。
* **测试主管 / 审核人员**：消费 Record 和生成的报告，做质量追溯或合规审查。
* **集成开发者**（间接用户）：通过 Capability 机制把具体测试设备/工具接入系统。

---

## 4. 核心场景

```text
工程师发现异常
   ↓（自然语言描述）
系统开始一次诊断 Workflow
   ↓
反复通过 Step 收集证据（读日志、查测试台状态、查询历史相似问题…）
   ↓
提出诊断/根因假设，展示已使用的证据
   ↓
视问题类型：
   ├─ 给出建议，工程师自行手动执行修复
   └─ 工程师确认后，系统执行受控的修复动作（如重启测试台、重新烧录）
   ↓
工程师最终确认问题已解决
   ↓
系统自动生成完整的诊断记录（Record）
   ↓
工程师 / 审核人员可随时基于该记录生成人类可读报告
```

---

## 5. 核心能力范围（In Scope）

* 自然语言问题接收
* 证据驱动、增量式诊断（复用 `WORKFLOW_SPEC.md` 的 One-Step Planning，见 `ADR-002`）
* 可插拔的 Capability 接入不同测试环境（domain-agnostic 核心 + 领域相关的 Capability 实现）
* 混合式问题解决：只读诊断建议 + 经工程师确认后的受控修复动作
* 完整的诊断记录，覆盖诊断过程的每一步和每一次人工确认/拒绝
* 基于记录按需生成人类可读报告——客户/工程师需要时生成，不需要时不生成，不是每次诊断的必需产出

---

## 6. 非目标（Out of Scope）

* **不是测试台本身的控制软件**——系统通过 Capability 集成到既有测试设备/工具，不取代它们。
* **不追求完全自主修复**——任何有副作用（会改变硬件/系统状态）的动作，默认都需要工程师显式确认才能执行。这一条直接约束了 `CAPABILITY_SPEC.md` 未来的分类方式（见 §8）。
* **不直接产出正式的合规认证文件**——生成的报告是内部参考材料，不是本系统的职责。
* **不绑定任何具体 HiL 测试平台或硬件协议**。

---

## 7. 成功标准（方向性，具体指标待 `REQUIREMENTS.md` 细化）

* 诊断耗时缩短，尤其是重复出现的问题类型。
* 每一次诊断都产出结构一致、完整可读的记录，杜绝"诊断完了但记录靠事后回忆补"。
* 团队的诊断知识能够被沉淀和复用（长期看可能反哺 Server 的 Knowledge Base，对应此前标记的 `KNOWLEDGE_SPEC.md` 待补项）。
* 工程师对系统给出的诊断/修复建议有足够信任，愿意采纳而不是绕开系统自己动手排查。

---

## 8. 关键约束（会影响下游文档的结论）

1. **修复动作分两类：只读诊断 vs 有副作用的修复，且两者都要支持** → `CAPABILITY_SPEC.md` 需要新增一个分类维度：Capability 是否 mutating（有副作用）、是否强制要求人工确认才能执行。当前版本没有这个维度。
2. **Domain-agnostic** → 任何具体测试设备协议都不应写死进核心 Spec，领域相关的东西一律通过 Capability 机制接入，核心 Workflow/Server 逻辑保持中立。

---

## 9. 核心术语对照

复用/扩展已有 Spec 的术语，不重新发明一套词汇：

| 已有术语 | 在本产品语境下的含义 |
|---|---|
| User Request | 工程师提交的自然语言问题描述 |
| Workflow | 一次完整的诊断-解决过程 |
| Step | 诊断过程中的一次具体动作（查日志、只读检查、经确认的修复动作等） |
| Evidence | Step 产生的观察结果，是诊断依据 |
| Completion Candidate / Completed | 系统认为问题可能已解决 / 工程师确认问题已解决 |
| **Record**（新概念） | Workflow 结束后生成的完整记录：原始 Request、全部 Step、全部 Evidence、全部人工确认/拒绝、最终结论。只要求完整、可读 |
| **Report**（新概念） | 基于 Record 按需生成的人类可读文档；是否生成、何时生成完全由客户/工程师决定，不是每次诊断的必需产出 |

`Record` 和 `Report` 是本文件引入的两个新概念，现有 Spec（`WORKFLOW_SPEC.md` / `CAPABILITY_SPEC.md` / `PROTOCOL_SPEC.md`）均未覆盖，具体需求见 `REQUIREMENTS.md` §5、§6。
