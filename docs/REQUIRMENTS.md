## 1. 主流程

1. 工程师提交自然语言描述的问题（可附带文件或环境信息）。
2. 系统创建 Workflow，开始逐步收集证据；工程师可随时查看进展、补充信息或纠正方向。
3. 系统基于证据提出原因假设，并展示支撑证据和尚未验证的部分。
4. 解决问题，分两种方式：
   * **建议**：系统给出具体可操作的建议；工程师自行执行，并把结果反馈给系统。
   * **受控执行**：系统提议一个有副作用的动作；工程师确认后才执行，拒绝则不执行。
5. 修复之后，系统收集证据验证问题是否消除。
6. 系统向工程师提出"问题可能已解决"，由工程师确认；工程师也可以选择"未解决，继续"，或放弃/取消。
7. Workflow 结束（任一结束状态）时，系统保存完整 Record。
8. 工程师需要时，基于 Record 请求生成 Report；不需要则不生成。

## 2. 功能需求

### 2.1 问题提交与诊断

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-1 | P0 | 工程师可以用自然语言提交问题，并可附带文件或环境信息 | 提交后系统创建 Workflow，并向工程师确认已开始 |
| FR-2 | P0 | 系统根据已获得的证据逐步决定下一步收集动作，不依赖预先固定的诊断脚本 | 同一类问题在证据不同时，系统执行的步骤序列可以不同 |
| FR-3 | P0 | 系统给出原因假设时，必须同时展示支撑它的证据（可定位到具体 Step/Evidence）以及尚未验证的部分 | 每个假设都能点到其依据的证据；不存在无证据支撑的结论 |
| FR-4 | P0 | 诊断进行中，工程师可查看已执行的 Step、已获得的证据和当前假设 | 任意时刻可查看，无需等到诊断结束 |
| FR-5 | P0 | 工程师可以在诊断中补充信息或纠正方向（例如"不是这个原因"） | 补充/纠正后，系统的后续步骤体现该输入 |

### 2.2 解决问题

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-6 | P0 | 系统支持"建议"方式：给出具体、可操作的修复建议 | 建议明确到工程师可以直接照做 |
| FR-7 | P0 | 系统支持"受控执行"方式；任何有副作用的动作，必须先获得工程师明确确认才能执行；工程师拒绝则不执行，且拒绝被记录 | 未经确认，有副作用的动作永远不会被执行；拒绝后系统重新规划 |
| FR-8 | P0 | 建议方式下，工程师可以反馈建议的执行结果，系统将其作为证据 | 反馈内容出现在后续诊断依据和 Record 中 |
| FR-9 | P0 | 修复之后（无论建议还是受控执行），系统先收集证据验证问题是否消除，再向工程师提出完成确认 | 不存在"修复后未经验证就请求确认"的路径 |
| FR-10 | P0 | "问题是否解决"由工程师确认；系统不得自行将问题判定为已解决 | Workflow 只有在工程师确认后才进入"已解决" |
| FR-11 | P0 | 工程师可以在任意时刻放弃或取消一个进行中的 Workflow；Workflow 的结束状态至少区分：已解决、未解决（放弃）、已取消、失败 | 各结束状态在 Record 中可区分 |

### 2.3 记录

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-12 | P0 | Workflow 以任一结束状态结束时，系统自动保存完整 Record：原始问题、全部 Step（目的、所用能力、输入）、全部 Evidence（含来源与时间）、全部人工决定（确认/拒绝/反馈/补充，含时间）、最终结果 | 每个已结束的 Workflow 都有对应 Record，且上述内容齐全 |
| FR-13 | P0 | Record 忠实于事实：只包含实际发生的步骤、实际获得的证据和实际发生的人工决定 | Record 中不存在未执行的 Step 或未获得的证据 |
| FR-14 | P0 | 工程师可以查看历史 Record（列表与详情） | 可按时间浏览，并打开单条 Record |
| FR-15 | P1 | 系统可检索历史 Record 中的相似问题，作为诊断参考 | 待 v0.1 之后设计；见 §8 |

### 2.4 报告

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-17 | P0 | 报告只在用户明确请求时生成，系统不得自动生成 | 不存在任何自动触发报告生成的路径 |
| FR-18 | P0 | 报告基于一份指定的 Record 生成；报告中的事实性内容必须来自该 Record，Record 中没有的信息不得写成事实 | 报告中每条事实性陈述都能在 Record 中找到出处 |
| FR-19 | P0 | 生成报告不改变 Record，也不触发新的诊断；同一 Record 可多次生成报告 | 生成前后 Record 内容一致 |
| FR-20 | P0 | 报告至少提供一种人类可读的输出形式 | 具体格式与模板见 §8 开放问题 |

### 2.5 集成

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-21 | P0 | 不同测试环境可注册各自的 Capability，无需改动核心 Workflow 逻辑 | 新增一种设备/工具的接入，不需要修改核心 Spec 或核心流程 |
| FR-22 | P0 | 每个 Capability 必须声明自己是否有副作用（是否会改变硬件/系统状态） | 系统据此决定是否需要工程师确认（FR-7） |

## 3. 非功能需求

| 编号 | 优先级 | 需求 |
|---|---|---|
| NFR-1 | P0 | **来源可追溯**：Record 中每条 Evidence 标明来源（哪个 Capability，或工程师输入）和产生时间 |
| NFR-2 | P0 | **持久性**：Record 保存成功后，不因系统重启或服务重新部署而丢失 |
| NFR-3 | P0 | **断线恢复**：网络中断后，进行中的 Workflow 可以恢复，已收集的证据不丢失 |
| NFR-4 | P0 | **并行**：同一工程师可以同时进行多个 Workflow |
| NFR-5 | P0 | **响应可感知**：工程师提交、确认、拒绝等操作后，界面应给出及时反馈；具体时延目标待取得基线后设定，本版本不预设数字 |
| NFR-6 | P0 | **安全前置**：认证、授权、沙箱等安全要求不在本文件定义，由后续安全规格承担（待建）；本文件仅规定 FR-7 的确认要求作为最低保障 |

---

## 4. 非目标

* 不提供审计或防篡改保证，不面向合规认证（`PRODUCT.md` D-3）。
* 不自动生成报告（FR-17）。
* 不处理多位工程师同时操作同一套物理硬件时的冲突（见假设 A-2）。
* 不定义具体的报告模板与格式（见开放问题 Q-4）。
* 不设计 Record 的编辑功能（见假设 A-3）。

---

## 5. 假设

以下假设由本文件为了推进而做出，需要产品方确认；若被否决，相关需求需同步调整。

| 编号 | 假设 | 影响的需求 |
|---|---|---|
| A-1 | Record 对**所有**结束状态的 Workflow 保存（包括未解决、已取消、失败），不只是"已解决" | FR-11、FR-12 |
| A-2 | v0.1 部署中，一套硬件在同一时刻只由一位工程师操作，因此不处理多人对同一硬件的冲突 | 非目标、FR-7 |
| A-3 | v0.1 中 Record 只读，不提供编辑/删除功能；这只是"不提供功能"，不构成防篡改承诺 | FR-12、FR-13 |
| A-4 | 请求生成报告的人就是提交问题的工程师 | FR-17 |
| A-5 | 建议方式下，修复结果通过工程师的主动反馈获得，系统不能自行得知 | FR-8 |
