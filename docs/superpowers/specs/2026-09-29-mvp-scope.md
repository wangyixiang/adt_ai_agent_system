# MVP 范围说明（v0.1 基础产品）

- **日期:** 2026-09-29
- **状态:** 待审阅（与 `ADR-003` 配套；批准后据其修订 Spec 并进入实现计划）
- **层级:** Scope — 基础产品做什么、做到什么程度算完成
- **关联:** `ADR-003-deployment-and-trust-model.md`、`PRODUCT.md` §5/§7、`REQUIREMENTS.md` FR-1~FR-24、`specs/*`

---

## 1. 目标

在**多用户共享 Server、每位工程师独占自己的测试台**（`ADR-003`）的部署形态下，跑通一条**完整的诊断-解决闭环**，并验证产品最核心的安全机制（受控执行）与全部新增协议要素。

**判断标准不是"功能多"，而是"闭环真的能走完、且异常路径不会造成重复物理动作或数据不一致"。**

---

## 2. 范围内（MVP 切片）

一条**完整闭环**：

```text
提交问题（自然语言）
  → 只读能力逐步取证
  → 假设 + 支撑证据（FR-3）
  → 受控执行：提议副作用动作 → 工程师确认 → 执行
  → 修复后验证
  → 工程师确认已解决
  → 保存 Record
  → 按需生成 Report
  → 提交人按需导出到第三方 Knowledge Base（导出半边）
```

具体覆盖：

| 能力 | 对应需求 |
|---|---|
| 自然语言提交 + 附件（小体积内联） | FR-1 |
| 证据驱动的逐步诊断（One-Step Planning） | FR-2、`ADR-002` |
| 假设与证据可见 | FR-3、FR-4 |
| 诊断中补充/纠正 | FR-5 |
| **受控执行**：确认 / 拒绝 | FR-7、`WORKFLOW_SPEC.md` §4.2 |
| **结果未知与对账**（`UNKNOWN`） | `WORKFLOW_SPEC.md` §4.3 |
| **幂等台账**（Client 持久化） | `WORKFLOW_SPEC.md` §4.3 |
| 修复后验证 → 完成确认 | FR-9、FR-10 |
| 取消 / 放弃（含 `CANCELLING` 收敛） | FR-11、`WORKFLOW_SPEC.md` §2.1 |
| 终止护栏（步数 / 重试 / `not_solved` / 时长） | `WORKFLOW_SPEC.md` §13 |
| Record 保存与查看（仅提交人） | FR-12~FR-14 |
| 按需生成 Report（markdown） | FR-17~FR-20 |
| 导出到第三方 Knowledge Base（半边） | FR-24（MVP 新增落实） |
| 身份、会话、Record 隔离（v0.1 不强制 TLS） | `ADR-003` |

## 3. 首批 Capability

不依赖真实 HiL 硬件，用软件能力 + 一个模拟副作用能力即可验证完整闭环：

| Capability | side_effect | interruptible | idempotent | 用途 |
|---|---|---|---|---|
| `filesystem.read_file` | false | true | — | 只读取证 |
| `git.collect_diagnostics` | false | true | — | 只读取证 |
| `terminal.execute_command` | true | false | false | 真实副作用路径（会弹确认） |
| `sim_rig.trigger_reset`（**模拟**） | true | false | false | 专门验证 `UNKNOWN` / 对账 / 幂等台账 |

> `sim_rig.*` 是本 MVP 引入的**模拟能力**（非 `CAPABILITY_SPEC.md` 的正式登记项），用于在没有真实测试台时验证安全机制；真实 `test_rig.*` 能力的接入留到后续迭代。

## 4. KB 导出半边（MVP 新增的最小协议面）

**语义**（呼应 `PRODUCT.md` D-5 与 `ADR-003` §6）：

* **提交人自己决定**是否把某条 Record/Report 沉淀给第三方 Knowledge Base。
* 导出对象**可选**：**Record（默认）** 或 **Report**。
* KB **是否接收**由其**审核人员**决定——审核完全在 KB 侧，**本系统不追踪审核状态**。
* 导出是 Server → KB 的**出站**行为，不经过 Client 执行本地操作。

**最小协议面（提案，最终形态留给后续 KB 集成 ADR）：**

```json
{ "type": "record.export_request",
  "payload": { "record_id": "rec_001", "object": "record", "target": "knowledge_base" } }
```

```json
{ "type": "record.export_result",
  "payload": { "record_id": "rec_001", "object": "record",
               "status": "ok", "error_code": null, "message": null } }
```

* `object` 取值 `record` | `report`。
* `status: "failed"` 时 `error_code` 取值：`export_unavailable` / `export_failed` / `invalid_object`。
* `record_id` 不存在仍走 `protocol.error`（code=`unknown_record`）。
* 导出**不修改** Record，可重复发起。
* 导出失败**不影响** Workflow 状态（此时 Workflow 早已终止）。

## 5. 完成标准

### 5.1 主路径（必须可演示、可回归）

```text
session.hello(auth) → session.welcome(user_id)
workflow.request("项目起不来了") → workflow.created
step.dispatch(filesystem.read_file / git.collect_diagnostics) → step.status(COMPLETED, evidence)
（系统展示假设与支撑证据）
step.dispatch(sim_rig.trigger_reset, requires_confirmation=true, idempotency_key=...)
  → step.status(WAITING, wait_reason=user_confirmation)
  → 工程师确认 → step.status(RUNNING) → step.status(COMPLETED, evidence)
step.dispatch(只读验证) → step.status(COMPLETED, evidence)
workflow.completion_candidate → workflow.completion_response(solved)
workflow.terminated(COMPLETED, record_id=rec_001)
record.get_request(rec_001) → record.get_response
report.generate_request(rec_001, detail_level=full) → report.generate_result(status=ok)
record.export_request(rec_001, object=record) → record.export_result(status=ok)
```

### 5.2 异常路径（必须可演示、可回归）

**E1 — 拒绝副作用：**

```text
step.dispatch(requires_confirmation=true) → WAITING(user_confirmation)
  → 工程师拒绝 → step.status(REJECTED, reject_reason.code=user_declined)
  → Server 不重试同一动作，重新规划（换只读验证 / human.manual_action）
```

**E2 — 超时 → `UNKNOWN` → 对账：**

```text
step.dispatch(sim_rig.trigger_reset, requires_confirmation=true, idempotency_key=idem_x)
  → 确认 → RUNNING → （模拟回包丢失，不再回报）
  → 超过 step_timeout → Server 判 UNKNOWN（不是 FAILED）
  → 生成只读对账 step → 裁定 COMPLETED / FAILED
  → 继续 Re-plan；若对账无果则退回工程师确认
```

**E3 — 断线重连恢复：**

```text
（Workflow RUNNING 中连接中断）
session.resume → workflow.state_sync(resumed=true, pending_step=...)
  → 继续执行原 Step
（若 session 已过期）
protocol.error(session_expired) → 重新 session.hello + 新 workflow.request
  → 旧 Workflow 宽限期后 FAILED(terminal_reason=client_unreachable) 并保存 Record
```

### 5.3 部署模型验收（`ADR-003` 配套）

* 两个工程师的 Client 同时连同一 Server，各自登录、各自跑闭环；
* 双方**互相看不到**对方的 Record；
* 未认证连接被拒（`protocol.error(code=auth_failed)`）；
* 传输为**明文**（v0.1 不要求 TLS，见 `ADR-003` §4；后续启用 TLS 不改应用层协议）。

## 6. 明确不在 MVP 范围

* 真实 `test_rig.*` 硬件能力的实现（先用 `sim_rig.*` 模拟）。
* KB 审核状态的回读与展示（只做导出半边）。
* 团队可见 / 角色化可见 Record；角色化审批。
* 沙箱、多租户、审计/防篡改、组织 SSO 联邦。
* 共享测试台（资源模型）。
* 跨 Client 续接同一 Workflow、多 Server 路由。
* 大体积附件走 blob 通道的完整实现（MVP 允许小体积内联；blob 通道可作为紧随其后的迭代）。
* `detail_level` 更多档位、Report 的 HTML/PDF 输出。
