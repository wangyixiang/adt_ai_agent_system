## 1. 主流程

1. 工程师提交自然语言描述的问题（可附带文件或环境信息）。
2. 系统创建 Workflow，开始逐步收集证据；工程师可随时查看进展、补充信息或纠正方向。
3. 系统基于证据提出原因假设，并展示支撑证据和尚未验证的部分。
4. 解决问题，分两种方式：
   * **建议**：系统给出具体可操作的建议；工程师自行执行，并把结果反馈给系统。
   * **受控执行**：系统提议一个有副作用的动作；工程师确认后才执行，拒绝则不执行。
5. 修复之后，系统收集证据验证问题是否消除。
6. 系统向工程师提出"问题可能已解决"，由工程师确认；工程师也可以选择"未解决，继续"，或放弃/取消。
7. Workflow 结束（任一结束状态）时，系统保存完整 Record。
8. 工程师需要时，基于 Record 请求生成 Report；不需要则不生成。

## 2. 功能需求

### 2.1 问题提交与诊断

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-1 | P0 | 工程师可以用自然语言提交问题，并可附带文件或环境信息 | 提交后系统创建 Workflow，并向工程师确认已开始 |
| FR-2 | P0 | 系统根据已获得的证据逐步决定下一步收集动作，不依赖预先固定的诊断脚本 | 同一类问题在证据不同时，系统执行的步骤序列可以不同 |
| FR-3 | P0 | 系统给出原因假设时，必须同时展示支撑它的证据（可定位到具体 Step/Evidence）以及尚未验证的部分 | 每个假设都能点到其依据的证据；不存在无证据支撑的结论 |
| FR-4 | P0 | 诊断进行中，工程师可查看已执行的 Step、已获得的证据和当前假设 | 任意时刻可查看，无需等到诊断结束 |
| FR-5 | P0 | 工程师可以在诊断中补充信息或纠正方向（例如"不是这个原因"） | 补充/纠正后，系统的后续步骤体现该输入 |

### 2.2 解决问题

| 编号 | 优先级 | 需求 | 验收标准 |
|---|---|---|---|
| FR-6 | P0 | 系统支持"建议"方式：给出具体、可操作的修复建议 | 建议明确到工程师可以直接照做 |
| FR-7 | P0 | 系统支持"受控执行"方式；任何有副作用的动作，必须先获得工程师明确确认才能执行；工程师拒绝则不执行，且拒绝被记录 | 未经确认，有副作用的动作永远不会被执行；拒绝后系统重新规划 |
| FR-8 | P0 | 建议方式下，工程师可以反馈建议的执行结果，系统将其作为证据 | 反馈内容出现在后续诊断依据和 Record 中 |
| FR-9 | P0 | 修复之后（无论建议还是受控执行），系统先收集证据验证问题是否消除，再向工程师提出完成确认 | 不存在"修复后未经验证就请求确认"的路径 |
| FR-10 | P0 | "问题是否解决"由工程师确认；系统不得自行将问题判定为已解决 | Workflow 只有在工程师确认后才进入"已解决" |
| FR-11 | P0 | 工程师可以随时表达放弃/取消一个进行中的 Workflow 的意图；具体何时生效取决于是否存在活跃且不可中断的 Step（见 `WORKFLOW_SPEC.md` §2.1：无活跃 Step、或 Step 可中断则立即生效；不可中断则等其自然结束后再终止）。Workflow 的终止状态为三种：已解决（`COMPLETED`）、失败（`FAILED`，系统判定无法继续）、已取消（`CANCELLED`，工程师主动终止，可选 `terminal_reason` 字段区分"取消"/"放弃"等具体意图，不构成独立状态）| 三种终止状态、以及 `CANCELLED` 的 `terminal_reason`（如有）在 Record 中可区分 |

## 4. 非目标

* 不提供审计或防篡改保证，不面向合规认证（`PRODUCT.md` D-3）。
* 不自动生成报告（FR-17）。
* 不处理多位工程师同时操作同一套物理硬件时的冲突（见假设 A-2）。
* 不定义具体的报告模板与格式（见开放问题 Q-4）。
* 不设计 Record 的编辑功能（见假设 A-3）。
* **不在本系统内建设知识库或历史案例检索能力**（v0.5 新增，v0.6 澄清）：FR-15 已删除，`PRODUCT.md` D-5。这条排除的是"系统内部自建检索引擎/案例匹配逻辑"，**不排除**对接第三方 Knowledge Base 做检索（见 FR-23）。Record 只承诺完整保存与可查看（FR-12~FR-14），不承诺"系统内检索"或"系统内知识复用"；Record/Report 是否被导出到第三方系统，v0.10 起由**提交人按需发起导出**（FR-24 的导出半边），但 KB 侧的检索与审核仍完全不在本系统内。
* **不做测试用例自动生成、不做测试执行编排**（v0.5 新增）：系统的介入点从"问题已发生"开始，主流程（§1）第 1 步的前置条件——是否要跑这个测试、测试计划如何编排——不在本系统职责内。
* **不对被测对象（DUT）的软件/固件进行代码级修复或生成修复建议**（v0.5 新增）：FR-6/FR-7 中的"建议"与"受控执行"作用于测试环境与工具（通过 Capability），不涉及对被测系统代码本身的修改建议。
